# PANDA — architecture audit (Phase 0)

Stack: Next.js 16 App Router, TypeScript, Tailwind, Vercel (Hobby), Vercel Blob for JSON state, Solana web3.js + wallet-adapter (Phantom), Pump.fun SDKs, Jupiter swap + Trigger API.

## What exists and is real
| Area | State |
|---|---|
| Home / discover / analytics | Real data (Pump.fun web API + Dexscreener + GeckoTerminal, failover). |
| Create coin | Real Pump.fun create + optional fee-sharing in the same tx. |
| Buy / sell | Real Pump bonding curve, PumpSwap, Jupiter; 1% PANDA fee visible in the wallet tx. Browser RPC goes through `/api/rpc` (allowlist, same-origin). |
| Portfolio / P&L | Positions derived on-chain (`derive-trade`, `backfill`); average-cost; flagged "estimated". |
| Rewards | Registry + per-mint ledger in Blob (ETag atomic updates), reserve-then-pay claims, per-claim and daily caps, alerts, solvency check in cron. |

| i18n, legal pages | EN/ES. |

## Wallet sign-in (Phase 2)
- `POST /api/auth/challenge` issues a one-time nonce (5 min) bound to wallet + domain; `POST /api/auth/verify` rebuilds the message server-side, verifies the ed25519 signature, atomically burns the nonce (ETag-locked Blob update; one blob per nonce) and sets an HttpOnly, SameSite=Strict, Secure, 2h HMAC-signed cookie. `GET /api/auth/session`, `POST /api/auth/logout`.
- `POST /api/rewards/claim` requires the session wallet to equal `holder`; also checks Origin. The client signs once per session via `useWalletSession`.
- Fails closed: without `AUTH_SESSION_SECRET` (>= 32 chars) sign-in returns 503 and nobody can claim.
- Tests: 22 unit tests + an end-to-end script (16 checks: wrong key, garbage/forged signature, replay, 8 concurrent verifies -> 1 login, forged/other-wallet cookie, cross-origin, claim without/with wrong/with right session).
- Limits: sessions can't be revoked server-side before their 2h expiry (logout only clears the cookie); used-nonce blobs accumulate in Blob until a cleanup job exists; Blob write atomicity was verified by design (same ETag mechanism as the rewards ledger) but the concurrency test ran against the dev in-memory store, not Blob.

## Audit trail + emergency pause (Phase 3)
- **Audit log** (`src/lib/audit`): every event is its own immutable Blob file (`audit/events/<day>/<id>.json`, never overwritten) with id, timestamp, actor, action, object, old/new state, reason, request ID; keys named like secrets are redacted (`redact.ts`) and each event is also written to the Vercel log. Recorded now: `auth.login`, `claim.paid|failed_onchain|outcome_unknown`, `token.create_tx_built` (actor marked `unauthenticated:` — that route has no session), `cron.collect_fees`, `protocol.pause|resume`, `admin.denied`. Not yet: fee-config changes beyond creation, reward calculation, epochs, airdrops (those systems don't exist yet).
- **Pause switches** (`src/lib/protocol`): independent per subsystem — `claims`, `airdrops`, `nft_minting`, `token_launches`, `reward_calculations`, `fee_processing`. Wired to: claims (`/api/rewards/claim`), token launches (`/api/pump/create`), fee processing (cron). Others get wired when their systems are built. Pausing stores a reason and deletes nothing. Public `GET /api/protocol/status` feeds the "PANDA PROTOCOL PAUSED" banner (EN/ES).
- **Fail closed**: if the pause state can't be read, the subsystem is treated as paused.
- **Admin** (`/admin`, `/api/admin/*`): enforced server-side — a wallet in `ADMIN_WALLETS` with a wallet sign-in from the last 30 minutes, same-origin check, rate limit, exact confirmation phrase ("PAUSE claims"), every change audited + alerted. Empty `ADMIN_WALLETS` = nobody is admin.
- Tests: 34 unit tests + 27-check end-to-end script (authorization, validation, pause/resume gating claims and launches independently, audit content and ordering, no secrets in output).
- Limits: audit recording is best-effort (a failed write is logged, doesn't block — so an emergency pause can't be blocked); audit blobs are readable by anyone with the URL (no secrets stored, wallet addresses and public signatures only); no hash-chaining, so it is append-only by convention, not tamper-evident; a pause reaches other server instances within ~5 s; the admin UI's signed-in view was type-checked but not clicked through with a real wallet; admin is a single-wallet check, not multisig.

## Fee distribution (Phase 4)
- Create form (`FeeDistributionStep`): PANDA 5% shown as a locked row (never an input); the creator splits the other 95% between Creator, Holders (PANDA's rewards pool) and an optional Partner wallet, with a live bar, presets, and an always-visible "PANDA 5% + allocations = 100%" line. Inputs parse as exact integer basis points (`parsePercentToBps`, max 2 decimals, no floats); a broken or unbalanced plan disables Launch and can never fall through to "no fee distribution".
- Final confirmation modal (`LaunchConfirm`) lists every recipient, address (abbreviated), percentage, total 100% and the first buy before the wallet prompt. Verified on desktop and 375px mobile, EN/ES.

- Rewards fix: the daily cron split holder credits with floating point (`Math.floor((amount/total)*distributed)` on UI amounts). Now raw integer balances + `splitPool`; the rounding remainder is stored as `dustLamports` in the ledger, and `creditHolders` refuses to write unless credits + dust == distributed exactly. Fuzz-tested.
- Tests: 44 unit tests total. Not covered: an on-chain create with a 3-way split (needs a real wallet and SOL); the create UI itself was checked in the browser through a temporary harness page, not with a connected wallet.
- Known: fee-sharing config authority — whether the creator or PANDA can later change a coin's split on-chain is a property of Pump's SharingConfig, not verified here; the UI therefore says the split is "written on-chain with your coin", not that it is permanent.

## PANDA Points + epochs (Phase 5–6)
Off by default: everything below is behind `FEATURE_PANDA_POINTS=true` (routes answer 404 otherwise).
- **Ledger** (`src/lib/points`): append-only events with deterministic IDs (`<signature>:<instructionIndex>:trade`, `correction:<id>`); `applyAward` is a pure, non-mutating function; a duplicate event never counts twice. One Blob document per wallet per epoch (awards to different wallets never contend), updated with the ETag-guarded update; integers only.
- **Formula v1** (`config.ts`, all numbers configurable and versioned): trade points = floor(sqrt(cumulative epoch volume / 0.001 SOL)); each trade earns the difference, so the total is identical however the volume is split (a first design applied the square root per trade and paid 14x more for slicing — caught by a test and replaced; fuzz-tested for path independence). Minimum trade 0.05 SOL; caps per wallet per epoch (5,000 per type, 20,000 total, 500 events).
- **What counts as a PANDA trade**: the confirmed transaction must contain a SystemProgram transfer of PANDA's fee from the trader to the treasury; volume = min(fee-implied volume, observed SOL movement). A trade made elsewhere earns nothing; the fee is real money paid, so volume can't be inflated on paper. Wired into `/api/portfolio/record-trade` (a points failure never fails the trade record).
- **Epochs** (`src/lib/epochs`): UPCOMING → ACTIVE → SNAPSHOT → CALCULATING → FINALIZED → DISTRIBUTING → COMPLETED, plus PAUSED (resumes only to where it came from). Transition table exhaustively tested; ACTIVE needs start time reached; SNAPSHOT needs snapshotTime + 10 min grace; FINALIZED is immutable (can't be paused, reopened or rolled back). Events are placed by their own timestamp and only recorded while the epoch is ACTIVE; late events are refused, not slipped into the next epoch.
- **Finalization**: totals (wallet-sorted, canonical JSON, sha256) are written once, never overwritten; an existing file must be byte-identical or finalization refuses; the hash is pinned on the epoch and re-verified on read (`totalsAreIntact`). This is the input the airdrop / Merkle phase will consume.
- **Corrections**: history is never edited; `/api/admin/points-correction` adds a new (possibly negative) event in the currently ACTIVE epoch, idempotent by `correctionId`, audited. A wallet's epoch total never goes below zero.
- **Admin API** (`/api/admin/epochs`: create / transition / finalize): admin session, same-origin, rate limit, exact confirmation phrases, audited; moves into CALCULATING / FINALIZED respect the `reward_calculations` pause switch.
- **Users**: `GET /api/points/me` (own points only, provisional until finalized; finalized epochs verified against the pinned hash) and public `GET /api/points/epochs` (no wallet data).
- **Storage abstraction** (`src/lib/storage/store.ts`): read / atomic update / create-once / list — the single file to replace when moving to a database.
- Tests: 79 unit/integration tests (incl. the full epoch lifecycle in the store) + a 34-check HTTP script with the flag on and a 5-check script with it off.
- Not done yet: no admin UI for epochs or points UI for users (the airdrop dashboard phase); other point types (launch, themes, NFT, campaigns, holding) have caps configured but no producers; anti-Sybil (only per-wallet caps today: many small wallets still multiply points); no leaderboard/rank (would need a cached snapshot, not a full scan per request).

## PANDA Airdrops (Phase 7–9)
Off by default: `FEATURE_PANDA_AIRDROPS` (publish/read) and, separately, `FEATURE_MERKLE_CLAIMS` (the endpoint that moves tokens). Both need the points system (`FEATURE_PANDA_POINTS`).
- **Allocation** (`src/lib/airdrop/allocate.ts`): from an epoch's PINNED points totals, amount = floor(pool x wallet points / total points), bigint only. The rounding remainder is returned as `dust` and recorded (policy `carry_forward`: the admin adds it to the next epoch's pool); sum(amounts) + dust == pool always; wallets whose share rounds to zero are dropped. The set is hashed (`allocationHash`) and re-verifiable end to end (`allocationIsIntact`).
- **Merkle tree** (`merkle.ts`): leaf = sha256(0x00 || epoch:wallet:amount), inner node = sha256(0x01 || left || right), unpaired nodes promoted (never duplicated), root commits to the leaf count (0x02). Verification also enforces the exact proof shape for the leaf's index, so an inner node can't be presented as a leaf (a test caught that a hash-only check accepted it).
- **Publish** (`POST /api/admin/airdrop`, admin, exact confirmation, `airdrops` pause switch): FINALIZED -> DISTRIBUTING only through this route (a manual transition to DISTRIBUTING is refused; only RESUMING a paused distribution is allowed). Recomputes from the pinned totals, stores the allocation once (never overwritten), pins root + hash + leaf count on the epoch. Refuses unless the airdrop pool wallet holds the tokens for this epoch AND for what every other published epoch still owes (they share one pool).
- **Claim** (`POST /api/airdrop/claim`): the wallet is the SESSION's (never a request field), the amount is the re-verified allocation (never a request field). Lifecycle persisted as REQUESTED -> SENT -> CLAIMED / FAILED (the spec's finer states happen inside REQUESTED/SENT). Rules enforced by `engine.ts` and exhaustively tested against a simulated chain: one atomic winner per wallet; the signed transaction's signature is stored BEFORE it is submitted; CLAIMED only when the transaction is FINALIZED; FAILED only when the chain proves it failed or its blockhash (+150 block margin for RPC lag) expired; a send error never causes a re-send (the chain decides); a crash at any point leaves a record that reconciles against the chain. Fuzz: 60 runs of random send failures, crashes, expiries and concurrency — no wallet is ever paid twice and every wallet ends up paid.
- **Integrity**: before any payout the stored allocation is re-verified against the epoch's pinned allocation hash, Merkle root and leaf count; anything that doesn't verify halts claims (and further publishes) and alerts — it is never trusted or repaired silently.
- **Users/public**: `GET /api/airdrop/me` (own amount, Merkle proof, claim status), `GET /api/airdrop/epoch?id=` (pool, distributed, dust, recipients, formula and the three pinned hashes; no wallet data). Only published numbers are shown, never estimates.
- **Trust model (be explicit)**: this is the off-chain, server-authorised variant — NOT trustless. The server holds the airdrop pool key and pays whoever the verified allocation says; the Merkle root is a public commitment users can check their proof against, but no on-chain program enforces it. A compromised server or pool key could pay arbitrarily from the pool. Mitigations: dedicated pool wallet funded per epoch, integrity checks, audit log, alerts, pause switch. Migration path: an on-chain Merkle-distributor program where the root is enforced by the chain.
- Tests: 112 total (allocation fuzz incl. pools above 2^53, Merkle for every tree size 1–70 and all tamper cases, claim engine incl. crash/uncertainty/concurrency/fuzz, real-store publish + multi-epoch solvency + tamper detection) and a 27-check HTTP script across three flag configurations. Not tested: the real token transfer (`solana-chain.ts`) — thin glue, needs devnet/mainnet with a funded pool.
- Not done: no user-facing UI yet (the airdrop dashboard is a later phase); no claim deadline or sweep of unclaimed amounts; no per-wallet share cap; anti-Sybil is a later phase (points caps only); the recipient's token account is created by the pool wallet (about 0.002 SOL each, paid by PANDA).

## NFT Themes + creation (Phase 10–11)
Off by default: `FEATURE_NFT_THEMES` (every route answers 404, the pages 404, and the nav link is hidden). Blob for storage, **Metaplex Core** for the NFTs, marketplace and branches are the next points.
- **Themes** (`src/lib/themes`): DRAFT → SCHEDULED → ACTIVE → CLOSING → CLOSED → ARCHIVED (or CANCELLED). The one gate every mint path calls is `mintDecision`: status ACTIVE **and** now inside [start, end). Both must hold, so a theme past its end stops accepting NFTs even if nobody flipped its status. Manual closing can only stop a theme *earlier*. Royalty capped at 10%, creation limit 1–100 per wallet, text without markup (multi-line allowed in rules/description).
- **Image pipeline** (`src/lib/nft/image.ts`, `sharp`): file type from the real leading bytes (never filename/MIME), SVG/HTML/other refused, ≤ 4 MB (Vercel rejects bodies over 4.5 MB), 256–8000 px, hard 40 Mpx decode limit (decompression bombs refused before decoding), static images only, and a fresh re-encode ≤ 2048 px that drops EXIF/GPS/ICC and any appended payload. **The unsanitized original is deliberately never stored** (it may carry GPS; Blob is readable by URL) — only its hash is kept.
- **Copy detection** (`dedupe.ts`): pixel hash (identical artwork in another format or with other metadata collides) → exact duplicate **rejected**; 64-bit perceptual hash within 8 bits → **REVIEW REQUIRED** (a resized/re-compressed copy; an admin approves or rejects, never auto-accused). Reservation is atomic, so two simultaneous uploads of one image can't both win; unfinished uploads expire after 24 h. Limits: a perceptual hash doesn't catch crops/mirroring/heavy filters and can't say who made an image first, only who uploaded first.
- **Mint** (`mint.ts`, non-custodial): the server only builds the transaction (one Core `create`, no other program); the wallet pays and owns, the asset key co-signs, the server signs nothing. Every asset gets `ImmutableMetadata`, `AddBlocker` (nobody can add plugins/lifecycle hooks later — otherwise a creator could make a sold NFT untransferable), and `Royalties` + `Attributes` (theme, theme id, content hash) with authority None. Royalty rule set is "None": **not enforced by the token** — PANDA's own market will honour it; other marketplaces may not.
- **Verification before "published"** (`verifyAsset`): the asset is read back from the chain and must match exactly — owner, name, uri, update authority, royalty, attributes — and the plugin check is an **allow-list** (a creator who edits the transaction to add a PermanentTransferDelegate, freeze/burn delegates, an oracle or lifecycle hook is never published). 30 tamper cases tested.
- **Flow** (`service.ts`, all I/O injected): upload → prepare → confirm. Per-wallet creation slots are atomic (8 simultaneous requests, exactly `limit` succeed); a theme that closes between upload and prepare refuses; a mint prepared in time may still finish after closing; a different asset key can only be requested after 3 minutes (the earlier blockhash has expired); confirm works **without a signature** for someone who closed the tab — nothing is taken on trust, the asset must match on-chain. `nft_minting` pause blocks upload/prepare but never confirm.
- **Routes**: `POST /api/nft/{upload,prepare,confirm}`, `GET /api/nft/mine`, `GET /api/themes[?slug=]` (only chain-verified NFTs are listed), admin `/api/admin/themes` and `/api/admin/nft-review` (exact confirmation phrases, audited).
- **UI**: `/themes`, `/themes/[slug]`, `/themes/[slug]/create` (5-step flow, EN/ES), same visual language; checked on desktop and 375 px mobile.
- **Tests**: 152 unit/integration tests (theme rules, image pipeline with real images incl. a decompression bomb, dedupe, Core transaction decoded with Core's own serializer, verification tamper cases, the whole service flow) and an ~80-check HTTP script (uploads real PNG/WebP/JPEG, builds a real Core transaction, closes a theme, pauses minting).
- **Fixed while doing this**: `new PublicKey(5)` accepted a number as an asset address; theme rules rejected line breaks; and a backslash lost in an earlier script had broken the rewards cron's holder-balance regex (`/^d+$/`), which would have credited nobody — fixed and covered by a test (commit 4e770c9).
- **Not verified / not done**: **nothing has been minted on a real network** — the Core create transaction is built and decoded correctly and the verification is tested against the deserializer's real shape, but the program-level behaviour of the plugin set (notably `AddBlocker` + authority-None plugins at creation) needs a devnet mint; the connected-wallet UI states (form, fees, signing) were not clicked through; AI image generation, content moderation beyond duplicates (no NSFW classifier), and permanent storage (Blob URLs are stable but not Arweave) are not implemented; images live on Blob URLs readable by anyone; the marketplace, secondary market and branches come next.

## NFT Marketplace (Phase 12–13): fixed-price listings, primary and secondary sales
Off by default: `FEATURE_NFT_MARKET` (list/buy/cancel + reading), and `FEATURE_NFT_SECONDARY` for anything that isn't the creator's first sale. Needs `PANDA_MARKET_AUTHORITY_SECRET_KEY` (a DEDICATED key, no funds) — without it every market write route answers 503 NOT_CONFIGURED (fail closed). Own marketplace, **no custom on-chain program** (I can't deploy and audit one from here), so it is server-authorised — the trust model below is the honest part.
- **How a listing works**: the seller approves PANDA's market authority as the NFT's Core `TransferDelegate` (one on-chain transaction the seller signs; the NFT stays in their wallet; Core revokes owner-managed delegates automatically on transfer) and signs the listing terms (asset, exact price, expiry, nonce, domain) with `signMessage`. The server stores that signature and **re-verifies it every time it is about to sign a sale**: a price edited in the database, or a listing the seller never made, can't produce a sale (tested).
- **How a sale works**: ONE transaction. The buyer is the fee payer and pays seller + creator royalty + PANDA's fee; the market authority pre-signs only the Core `TransferV1` to the buyer. Its signature covers the whole message, so payments can't be dropped or altered afterwards; it holds no funds, so it can never spend anyone's money. Payment and NFT arrive together or not at all.
- **Fee and royalty** (`src/lib/market/config.ts`, `split.ts`): **PANDA's market fee is 2% (`feeBps: 200`) — my default, not something you specified; change it in one line.** Royalty = the NFT's own on-chain royalty (theme's, max 10%), paid on secondary sales only. Primary = the creator selling their own NFT for the first time. Integer lamports; fee + royalty + seller always equals the price (4,000-case fuzz). The buyer pays exactly the listed price and sees the exact split before signing.
- **Nothing is recorded until it is verified**: the landed transaction is fetched and must be EXACTLY the specified payments plus one Core transfer of this asset to the buyer, signed by exactly the buyer and the market authority (18 tamper cases tested). One transaction signature can belong to one sale only, and a sale completes once, so volume and floor are real — no wash-inflated stats. Confirming works without a signature (closed tab) by checking the NFT's latest transactions.
- **Only safe NFTs trade**: the same allow-list check as minting (no permanent/freeze/burn delegates, hooks, oracles...), plus the market's own delegate; only the on-chain OWNER can list; one active listing per NFT (atomic); a listing whose NFT was moved or whose approval was revoked is closed instead of sold.
- **Pause**: new `nft_market` subsystem. It blocks listing and buying; it never blocks cancelling or confirming an in-flight sale (a seller can always take a listing down).
- **API**: `POST /api/market/{list/prepare,list/confirm,buy/prepare,buy/confirm,cancel}` (session, same-origin, rate limited, one shared gate), public `GET /api/market/listings?theme=`; UI: Buy/Sell/Cancel on each NFT card with a confirmation dialog showing the exact split (EN/ES), stats (listed, floor, volume, sales) and recent sales — all from verified data.
- **Tests**: 187 total. Market: split fuzz, terms, real Core list/cancel/sale transactions decoded, 18 landed-transaction tamper cases, and 13 service scenarios (primary, secondary with royalty, non-owner, unsafe assets, forged signature, DB price edit, stale listing, fake sale, reused signature, closed tab). HTTP script in three flag configurations (off / no key / full: 34 checks).
- **Trust model, plainly**: the market authority key can transfer any NFT whose owner has approved it (that IS a listing) to anyone, without payment, if it is stolen or misused. Mitigations: it holds no funds; sellers can revoke on-chain at any time (Cancel does it); rotate the key if compromised; keep it out of the repo/logs. This is weaker than an on-chain escrow program, which is the upgrade path.
- **Not verified / not done**: **never run on a real network** — above all, that the Core program accepts adding an owner-managed `TransferDelegate` on assets created with `AddBlocker` (I believe AddBlocker only blocks authority-managed plugins; if it also blocks this, listing fails and the mint plugin set must change) and that `removePlugin`/`transfer` behave as built. Offers/bids are NOT built (they need escrow or a live buyer; a non-escrowed offer design is the honest option); no collection/branch pages; wallet-connected UI (dialogs, signing) not clicked through; a purchase already signed by the buyer within ~2 minutes can still land after the seller cancels (it is verified and recorded like any sale); `getSignaturesForAddress` recovery depends on the RPC.

## Anti-abuse (Phase 15): wash trading and Sybil farms
Same flag as points (`FEATURE_PANDA_POINTS`). **It detects and proposes; a person decides.** No signal proves abuse, so the design is built around not punishing honest users.
- **Signals** (`src/lib/abuse/signals.ts`, all thresholds in `config.ts` under version `v1`): NFT market — an NFT returning to a previous owner (2–N wallet cycles), one counterparty dominating a wallet's sales, repeated buy-and-resell within minutes, buyer/seller funded by the same wallet; trading — buy/sell of the same coin within minutes at like-for-like size, many identical trade sizes (weak on purpose); Sybil — 5–30 wallets first funded by the same address, brand-new wallets (weak), a group of 8+ wallets repeatedly making their first trade of the same coins inside the same minute; velocity — near the per-wallet event cap. A funder with more than 30 wallets is treated as an exchange/faucet and says nothing. PANDA's own wallets and admins are never analysed.
- **Score** (`score.ts`): integer risk points 0–1000 and confidence 0–100. A signal is worth points x confidence, so guesses add little. Each **family** of evidence is capped (450) below the RESTRICTED line, so **one kind of evidence can never get a wallet past REVIEW**; RESTRICTED needs 2+ families, score >= 500 and confidence >= 60; DISQUALIFIED score >= 800 and confidence >= 70. Tested with a wash farm (proposed RESTRICTED), a coordinated pair (REVIEW only) and an honest scenario (busy trader, creator selling to different fans, a hot-launch crowd, friends funded by one person, 200 exchange-funded wallets) that must flag nobody, plus a fuzz for monotonicity and bounds.
- **Statuses and effects** (`policy.ts`): NORMAL and REVIEW change nothing for the wallet (REVIEW only puts it in front of a person and is never shown to the user). RESTRICTED and DISQUALIFIED stop new points (`wallet_restricted`; admin corrections stay possible) and hold the wallet's points out of any epoch finalized while they are in force — the totals record who was held out and how much (`excluded`, inside the hash; epochs with nobody excluded keep their exact old hash). Finalized epochs are never touched retroactively. **The engine can only open REVIEW on a NORMAL wallet**; it never escalates and never overrides a person. Admin decisions need a reason and an exact confirmation phrase, and are audited.
- **Analysis run** (`run.ts`): reads the points ledger, trade logs, completed sales and on-chain wallet history (first transaction / first SOL funder, cached forever once the wallet's true beginning was reached; a wallet with more history than we follow claims neither an origin nor a funder — never a guess). Bounded (400 wallets, 150 lookups, 18 s) and it says so: the immutable report (`abuse/reports/<epoch>/<run>.json`) records the config version, coverage (wallets, trades, sales, profiles used/missing, budget reached), every finding with reason codes and evidence, and who ran it.
- **API**: admin `GET/POST /api/admin/abuse` (analyze, decide, resolve_appeal; reports, flagged wallets, a wallet's history); wallet `POST /api/abuse/appeal` (only RESTRICTED/DISQUALIFIED, one open at a time, 20–1000 characters, 10/h). `GET /api/points/me` shows `restriction` (status, reason codes, appeal state) only to a wallet that is actually restricted. Accepting an appeal does NOT clear the wallet — that is a separate decision.
- **Tests**: 224 total (37 new): every detector with positive and negative cases, scoring thresholds, fuzz, state machine, appeals, profile lookup with a fake chain, the full run against a farm (only REVIEW applied, honest wallets untouched, re-run idempotent, cached profiles, failing RPC = no claims, time budget), exclusion in totals and tamper checks; HTTP script (60+ checks, plus flag off).
- **Not verified / not done**: **never run on real data — every threshold is a reasoned guess until calibrated against a real epoch** (run it first and read the findings before trusting REVIEW flags); the Sybil defense is a heuristic (it sees shared funding and timing, not identity: a patient farmer with separately funded wallets is invisible, and an honest group funded by one person still gets flagged for a look); profile lookups cost RPC calls and very old/busy wallets are skipped; trade evidence only covers trades logged through PANDA; no admin UI (API only) and no user-facing appeal UI; reports are Blob files readable by anyone with the URL and contain wallet addresses and reason codes — decide whether that is acceptable before going public; rate limits are per instance.

## Portfolio (Phase 19): value, P&L, allocation, activity, rewards
No feature flag: it only READS (the wallet's real balances from Solana, PANDA's trade log, the rewards ledgers). Nothing is custodied or moved.
- **The rule: never claim more than is known** (`src/lib/portfolio/view.ts`, pure and tested). Each holding's P&L is one of three: **tracked** (trades PANDA recorded live that cover the whole balance you hold now), **estimated** (history read back from the chain, partial history — a sell with no known purchase — or a balance that doesn't match the log; shown with "≈" and a chip), or **unavailable** (no known purchase price or no live price: no number at all). Before this phase a position without a live price showed "+$0.00 · 0%"; it now says Unavailable. SOL itself has no P&L. The totals say how many holdings they cover ("Based on 2 of 6 holdings") and how many holdings had no price and are left out of the total value.
- **Sections**: total value; open P&L and realized P&L (each with its tracked/estimated chip); holder rewards (claimable / earned / claimed SOL, exact lamports summed over the rewards ledgers of every registered coin, with a link to Rewards where claiming stays behind the signed-in session); allocation (top 5 + other, integer basis points that always sum to exactly 10 000); holdings with image, name, ticker, amount, value, average entry and P&L (sort by value / recent / profit) and closed positions; recent activity (the wallet's latest trades with links to the coin and the transaction). UI is EN/ES, split into a presentational `PortfolioView` and the data-loading `PortfolioClient`; checked visually on desktop and phone width in both languages.
- **API**: `GET /api/portfolio/positions?wallet=` (now also returns `recent`) and new `GET /api/portfolio/rewards?wallet=`. Both are public read-only (a wallet's data is public on-chain), validate the address and are rate limited per IP, because a first visit scans the chain and each rewards call reads storage (rewards reads at most 120 ledgers per call and reports `partial` if there are more).
- **Tests**: 235 total (11 new): positions honesty (price known/unknown, realized profit, partial history), every tracked/estimated/unavailable case, summary and realized totals, allocation (fuzz: integer bps, non-negative, sorted, sum 10 000), rewards aggregation (incl. prototype-key wallets).
- **Not verified / not done**: never viewed with a real connected wallet (the page was checked with made-up data passed through the real logic; the wallet, RPC and price calls were not exercised); P&L uses average cost (not FIFO) and the SOL amounts recorded per trade, so fees may not be fully reflected; the trade history outside PANDA covers only the last ~80 transactions and only SOL-priced swaps; "recent activity" shows trades only — reward claims are not logged per wallet (the ledger keeps totals), and token creation / graduation / fee events belong to the Activity feed phase; NFTs and points are not in the portfolio yet; a wallet's portfolio is viewable by anyone who knows the address only through the API (the page shows the connected wallet).

## Activity feed (Phase 20): real events with a transaction to check them against
Public page `/activity` (footer + a link from the home feed) and public read-only APIs `GET /api/activity/feed?filter=&mint=&limit=` and `GET /api/tokens/:mint/activity`. No flag: nothing here moves funds.
- **Two kinds of source, kept apart** (`src/lib/activity/`). (1) **The journal** — events PANDA itself verified on-chain when they happened, appended to one document per day (idempotent by event id, capped per day, every field validated, presentation fields such as ticker/logo never stored): a fee distribution (recorded by the fee cron after the `distributeCreatorFees` transaction confirmed and its effect on the pool was measured; `collectFeesForMint` now also returns the signature and block time), a reward claim (after the payout confirmed), a trade made through PANDA (after the transaction was fetched and the wallet's real balance change matched the claimed side), and a launch (after the on-chain fee-sharing config was verified, dated by Pump.fun's own launch time — not recorded if Pump.fun doesn't know the coin). These carry a ✓ in the UI. (2) **The market indexer** — GeckoTerminal (pool trades, PumpSwap pools) and Pump.fun's public API (launches, graduation status), isolated in `deps.ts` behind the `FeedDeps` interface so a provider can be replaced by editing one file.
- **Events** (all seven of the spec): launch, buy, sell, large trade (>= 5 SOL, a flag on trades computed here — a source can't set it), fee distribution, reward, graduation. Every event links to its coin and, when it has one, its transaction (Solscan). The same event from the journal and an indexer is one event and the PANDA-verified copy wins. Graduation = a recent PumpSwap pool of a coin Pump.fun says has graduated, dated by the pool's creation.
- **Honesty**: each source reports `ok`/`unavailable` and the page says which ones are down instead of showing an empty list as if nothing happened (a first version treated a GeckoTerminal 429 as "no trades" — found on real data and fixed with a strict fetch that throws). Flagged (NSFW/banned) coins are never shown; launches need real traction ($8K market cap) because the raw launch stream is mostly dust; trades under 0.01 SOL are dropped; events older than 3 days or dated in the future are dropped; in the mixed view trades take at most 60% of the feed so they can't bury launches, graduations, fees and rewards.
- **Safety of the routes**: filter/mint/limit validated, 60 requests/min per IP, 20 s server cache, so the third-party indexers aren't called per request.
- **Tests**: 255 total (20 new): journal validation and idempotency, mappers (exact lamports, junk dropped, flagged coins, graduation window), dedupe and precedence, large flag, filters, the trade-share rule, a fuzz over the merge, per-source failure reporting, cache. Run against the real indexers in dev: 48 trades, 3 launches, 7 graduations, and a genuine Pump.fun rate limit correctly reported as unavailable.
- **Not verified / not done**: the journal hooks (fee cron, claim, record-trade, register) were type-checked and the journal is tested, but **no real fee distribution, claim or PANDA trade has been recorded end to end** (nothing has run on mainnet); the market feed depends on two free third-party APIs that rate-limit (GeckoTerminal returned 429 during testing) — a paid tier or an own indexer is the real fix; it only sees the ~8 most active coins' latest trades, launches with traction and graduations of active pools, so it is a "what's happening" view, not a complete ledger; "large" is a fixed 5 SOL threshold; the feed is polled every 30 s (no websocket); no per-coin activity panel on the coin page yet (the API exists); events aren't reorg-checked beyond `confirmed`.

## Analytics (Phase 17): PANDA's economy, one kind of money per card
`/analytics` keeps its market section (live from Solana, over the coins Discover tracks — now labelled "Market volume (24h, USD)": the whole market, not PANDA) and gets a **PANDA economy** section fed by `GET /api/analytics/economy` (public, read-only, 30 req/min/IP, 60 s cache). The rule from the spec: **never combine incompatible metrics** — every card has its own unit chip and its own source line, and nothing is summed across cards.
- **Volume through PANDA (SOL)**: trades made through PANDA, counted only after `record-trade` fetched the confirmed transaction (the wallet's real balance change). All-time total, last 7 days and a 14-day bar series.
- **PANDA fees (SOL)**: two separate lines — the 1% trade fee (only counted when the transaction really contains the transfer to the treasury, via `findPandaFee`) and PANDA's share of creator fees.
- **Creator fees distributed (SOL)**: for every `distributeCreatorFees` the cron sends, the split is **read from that transaction's own balance changes** (`collectFeesForMint` now uses the parsed transaction and returns each shareholder's real payout; the payer's share has the network fee added back): to the holders' Rewards Pool, to PANDA, to creators and partners — the parts always add up to the whole.
- **Holder rewards (SOL)**: credited (excluding rounding dust, shown apart), claimed, waiting — summed from the rewards ledgers of up to 120 coins, `partial` if there are more.
- **Airdrops (PANDA token, not SOL)**: per epoch, published vs claimed, exact in big integers, shown with the mint's real decimals (or as raw units, labelled, if they can't be read). An epoch whose published data fails its integrity check is left out and named, never trusted.
- **NFT market (SOL)**: primary and secondary volume kept apart, market fees and royalties, completed sales only.
- **Check it yourself**: the treasury and Rewards Pool addresses (and the token mint, if configured) link to Solscan (spec §40, partly — see below).
- **How PANDA's own totals are kept** (`src/lib/economy/rollup.ts`): one document per day plus an all-time document, only added to, from `recordActivity` and only when the journal says the event is NEW, so recording the same transaction twice can't count twice. If the day's journal is full the event is counted as `dropped` and the card says "this is a minimum". A crash between the journal write and the totals write can undercount by one event (documented, accepted for now). Counting starts at the first recorded event and the page says since when — there is no backfill of history from before.
- **Honesty**: a section that can't be read is `null` / "unavailable", never a zero (seen in dev without Blob: rewards came back unavailable while the rest answered); empty sections say "Nothing recorded yet".
- **Tests**: 270 total (15 new): delta validation, overflow, day/total accumulation and zero-filling, counted-once and dropped-when-full, the split from balance changes (payer fee, unknown accounts, treasury == pool), every section builder, exact big-integer airdrop sums, SOL/token formatting, per-section failure. Checked visually with made-up numbers (all cards, empty states) on desktop and phone width in both languages, and against the real API.
- **Not verified / not done**: nothing has run on mainnet, so **no real trade, distribution or claim has fed these totals yet**; the trade fee counts only trades made through PANDA's own trading UI (`record-trade`), and the volume card is PANDA's own volume, not the market's; "PANDA fees" does not include NFT market fees (they are in the NFT card, kept apart on purpose) or the buy-back; the split read from a distribution transaction assumes the shareholders are the ones in the coin's fee-sharing config; rewards "claimed" is what the ledger books as claimed (it can include a payout whose outcome is still unconfirmed); no per-coin analytics, no time ranges beyond 7/14 days, no export; part of the Analytics page header/trending text is still English-only (existing gap for the UX pass); spec §40 asks every reward system to also show its formula, eligibility and distribution date — only the source, pool and on-chain addresses are shown here.

## NFT branches (Phase 14): THEME -> BRANCH -> NFT
Off by default: `FEATURE_NFT_BRANCHES` (needs `FEATURE_NFT_THEMES` too). Spec §25–26; §33 (a token per NFT) is deliberately NOT built — the spec forbids it without an economic audit.
- **What a branch is** (`src/lib/branches/`): a sub-collection of one theme, opened by a creator who earned it. The parent theme is only read, never modified (its published list isn't touched either: a branch's NFTs are listed under the branch). Statuses ACTIVE / PAUSED / CLOSED; a creator can close their own branch for good, pausing and resuming are admin decisions (`POST /api/admin/branches`, exact phrase such as "PAUSE BRANCH 3", reason, audited); CLOSED is final.
- **Permissions are explicit**: only the creator and the wallets they list (at most 5, added and removed by the creator alone, atomically) can add NFTs; a contributor can't manage anything; a stranger is refused at upload (403) and re-checked at prepare, so a contributor removed mid-flow can't finish. The acting wallet is always the session's, never a request field.
- **Eligibility** (`eligibility.ts`, thresholds in `config.ts` under `v1` — the spec's own examples, meant to be tuned): 50 unique buyers, 1 SOL of legitimate volume, a 24 h holding period, no abuse flags. It is **always recomputed on the server from PANDA's verified sales** (a client claiming eligibility changes nothing — tested over HTTP). A sale does not count when: the buyer is the seller or the creator, the NFT came back to a previous owner (wash pattern), the buyer or seller has ANY abuse status (review, restriction, disqualification), or the buyer hadn't held it 24 h (quick flips, and purchases still inside the holding period). Volume counts only counted sales, so a ring can't inflate it by flipping. Measured over **all of the creator's NFTs in that theme**: a single 1-of-1 can only have one owner at a time, so "50 unique buyers" of one NFT would be unreachable — this interpretation is mine and is documented in the UI. The creator sees each criterion, what they have, how many sales didn't count and why.
- **Caps**: one open branch per creator per theme, five overall, 20 NFTs per wallet per branch, 1,000 per branch, all atomic (racing creations can't get past the cap — tested).
- **NFT creation in a branch** reuses the same upload -> prepare -> confirm pipeline. Differences: the NFT is **named and numbered by the server** ("Cyber Wolf #001"; a refused upload never burns a number, an abandoned one leaves a gap), the branch's rules replace the theme's schedule (a branch **keeps minting after its theme closed** — tested with a CLOSED theme), the creation slot is a separate scope from the theme's, the parent theme's royalty applies, and two extra on-chain attributes (`Branch`, `Branch ID`) are written and **verified back from the chain** like every other attribute (one function, `attributesOfRecord`, used by the mint, the confirmation and the market). NFTs minted before branches existed are unchanged. Branch NFTs trade in their parent theme's market (that is where their listings and sales are recorded).
- **API**: public `GET /api/branches?theme=` / `?slug=`; signed-in `GET /api/branches/eligibility?theme=`, `POST /api/branches/create`, `POST /api/branches/manage` (add/remove contributor, close); the upload and `mine` routes accept a branch. UI: a Branches section on the theme page (list, and for a connected wallet the eligibility panel with the methodology and, when eligible, the form), a branch page with its verified NFTs and a management panel for the creator, and the existing create-NFT page working for branches. EN/ES; checked visually on desktop and phone width.
- **Tests**: 299 total (29 new): eligibility (thresholds, whale, self-purchases, wash return, flags, holding period, a fuzz that flags can only reduce what counts), rules and permissions, creation caps and races, serial numbers under concurrency, the branch NFT flow against a closed theme, no-hijack checks, paused/closed branches, on-chain attribute mismatch; HTTP script (flag off / on).
- **Not verified / not done**: nothing has been minted on a real network — above all that the `Branch` attributes verify against a real Core asset; the positive path (a creator who actually qualifies opening a branch) is covered by unit tests but not over HTTP or the UI with a real wallet (that needs real sales); the eligibility can't see coordinated wallets that the anti-abuse engine hasn't flagged (it relies on it); "ranking", community signals and PANDA Points for branches (§26/§31/§32) are not built; theme reward pools (§30) are not built; no admin UI for branches (API only); branch pages have no analytics of their own yet; a branch's sales are counted with its theme's market stats.
